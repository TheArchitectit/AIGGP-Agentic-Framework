# DevGate-Agentic-Framework — Full QA & Gap Analysis

**Date:** 2026-09-13 · **Auditor:** Instinct (external QA, read-only on main)
**Target:** `TheArchitectit/DevGate-Agentic-Framework` @ `c5827c4` (main, 50 commits past v1.0.0)
**Method:** every file read (58 files, ~21k lines), all gates run against the repo itself and against fixture consumer projects (submodule layout and standalone), npm-audit classification tested against a live registry query, 44/44 existing tests pass (`pytest tests/`), prior 2026-09-09 QA findings re-checked.

## Verdict

The framework's core is real and much improved since the 2026-09-09 QA: the overlay merge contract is implemented consistently, the diff scanner is hunk-accurate, the registry regression arm fails loud on shallow checkouts, and the test suite locks several prior failure classes. **But the perimeter is still leaky: two gates are completely broken (scene inventory fails every valid Godot scene; the semantic scanner crashes on a standalone checkout), the test runner and the `--all` regression arm pass green while scanning nothing in exactly the CI layouts they are sold for, the npm audit gate still downgrades direct runtime vulnerabilities to warnings, the deploy pipeline still gates the submodule instead of the project, and 19 of 42 shipped rules are dead config that no gate enforces.** Three of the six gaps called out on 2026-09-09 are still open.

Severity counts: 6 critical/high-confidence correctness breaks, 8 high, 11 medium, 8 low/cosmetic. Every finding below carries file evidence; `[verified]` means reproduced live in this audit, `[code-read]` means established by reading the code path end to end.

## CRITICAL / HIGH — gates that fail closed on valid input or green-light unscanned work

### C1. `scene_inventory.py` fails every valid Godot scene — "parse error" [verified]
`scripts/scene_inventory.py:47-49`: `parse_tscn_buttons()` calls `ET.parse(scene_path)` first; `.tscn` is not XML, so `xml.etree.ElementTree` raises on every valid scene and the function returns `([], "parse error")` before reaching its own regex parser (lines 51-75, unreachable). Reproduced: a minimal valid `HUD.tscn` exits 1 with `FAIL src/UI/HUD.tscn: parse error`. The gate cannot parse any valid input — same finding as 2026-09-09, still present. Additionally the regex path that never runs compares connection `from="Panel/PlayButton"` (a node path) against bare button names, which would false-positive orphans on nested buttons even if reached.

### C2. `semantic-scan.mjs` crashes on standalone checkouts — scans the parent directory [verified]
`scripts/semantic-scan.mjs:29-44`: `findProjectRoot(resolve(devgateRoot, ".."))` walks up looking for markers; when none exist (standalone DevGate clone in a markerless directory) it returns the walk's start dir — the *parent* of the repo — and `walk()` recurses it without error handling. Reproduced from `/tmp/devgate`: `semantic-scan error: EACCES: permission denied, scandir '/tmp/git_remote_s3_fetch_9ax_qwz1'`, exit 1. This is the exact escape `guardrails-scan.mjs` fixed and documented in its header comment ("the old implementation walked UP … scanning every sibling repo"); the fix was never ported to `semantic-scan.mjs` or `run-tests.mjs` (same `findProjectRoot`, lines 41-55).

### C3. `run-tests.mjs` passes green running zero tests on standalone DevGate [verified]
`scripts/run-tests.mjs:58` anchors `PROJECT_ROOT` via the same walk-up; from a standalone checkout it escapes to the parent (`/tmp`), finds none of `dist|test|tests|src`, and reports `TOTAL: 0 passed, 0 failed across 0 files` — exit 0 while the repo's own 6 test files sit unrun. The framework's flagship "silent success" failure mode, in its own runner. Separately, test discovery only looks in `dist/ test/ tests/ src/` (`main()`, lines 205-212) while the README and AGENTS.md promise test files are found "anywhere in your project" — tests under `pkg/`, `scripts/`, or the repo root are silently never run.

### C4. `run-tests.mjs` Rust arm runs 0 tests and passes [code-read]
`scripts/run-tests.mjs:117-122`: for `*_test.rs` it runs `cargo test -- <file-stem>`. Cargo's positional filter matches **test function names**, not file stems, so a file `tests/plugin_smoke_tests.rs` containing `fn test_plugin_loads()` runs zero tests; cargo exits 0 ("0 passed"), the runner's pass parser counts no failures, and the file reports ✓. The correct invocation for integration targets is `cargo test --test <stem>`.

### C5. `regression_check.py --all` pattern arm is vacuous in a clean CI checkout, while the docs and drift template claim a full-tree sweep [verified]
`scripts/regression_check.py:370-376` (`main()`): under `--all`, `staged=True, unstaged=True`, so the pattern-rule arm (`run_regression_check` → `get_changed_files`) scans only the *working-tree* diff — empty in CI — while the registry arm (`get_added_lines(all_scope=True)`) correctly scans `tag...HEAD`. The two arms disagree about what `--all` means, and neither scans the full tree. Verified: committed a critical PREVENT-007 (`except:`) violation after tag `v0.1.0`, clean tree, `--all --pre-commit` exits 0 with "No potential regressions detected". Yet `templates/github-workflows/drift-scan.yml` header says the job "runs DevGate's scanners against the whole tree (not a diff), so pre-existing code … is re-swept", and the tool's own warning says `--all` "scans every change since the last tag" — false for the pattern arm. The README's own note admits there is no per-PR scope either ("DevGate has no flag to scope the regression scan to an arbitrary base ref").

### C6. npm audit gate downgrades direct runtime HIGH/CRITICAL vulns to warnings [verified]
`scripts/regression_audit.py:60`: `is_runtime = any(eff in runtime_deps for eff in effects)`. In npm's audit format, `effects` lists a vuln's *dependents* — for a direct dependency it is typically `[]` — so a HIGH vulnerability in a direct runtime dependency classifies as dev-only and never blocks. Verified live: `lodash@4.17.15` as a direct dependency (`isDirect: true`, `effects: []`, HIGH, GHSA-35jh-r3h4-6jhm) → `blocking: 0, warnings: 1, is_runtime=False`. The correct signal is npm's own `isDirect` flag plus `effects`. Same finding as 2026-09-09 ("npm audit can miss HIGH/CRITICAL runtime vulns"), still present.

### C7. `deploy.sh` gates the DevGate submodule, not the project being deployed [verified]
`scripts/deploy.sh:56` (`cd "$ROOT"`) runs `regression_check.py --all --pre-commit` from the DevGate directory. `regression_check.find_project_root()` walks from CWD and stops at `.devgate/.git` (a submodule always has one), so the release gate audits the submodule's own `scripts/` tree and diff — the project's code is never regression-gated before publish. Verified: with a `.git` present in `.devgate`, root resolution returns the `.devgate` directory. Same finding as 2026-09-09 ("deploy.sh audits the DevGate submodule history instead of the consuming project"), still present. Note the adjacent `guardrails-scan.mjs` invocation *does* target the project (it anchors on script location), so the two deploy gates evaluate different repositories.

## HIGH

### H1. 9 of 10 enabled semantic rules are dead config [verified]
`.guardrails/prevention-rules/semantic-rules.json` ships 10 enabled rules; `scripts/semantic-scan.mjs` implements exactly one (SEMANTIC-001). SEMANTIC-002 (resource leak), -003 (missing auth decorator, error), -004 (Godot @onready, error), -005 (React useEffect — advertised in the README's semantic-scan section and the script's own header comment), -006, -007 (error), -008 (error), -009, -010 (error) have no enforcement anywhere. Consumers reading the rules file believe they have AST coverage they do not have.

### H2. `drift-scan.yml` template produces a permanently red regression gate [code-read]
Both `actions/checkout@v4` steps in `templates/github-workflows/drift-scan.yml` use the default `fetch-depth: 1`. `regression_check --all` needs tags/history (`resolve_all_base` → `git describe --tags`), and since the FAIL-3bc44d38 fix it now *raises* `RuntimeError` when the base can't be diffed — so the scheduled drift job fails every run on the regression arm. Same finding as 2026-09-09 ("drift CI template uses shallow checkout though the gate needs history"), still present. The same job also runs `semantic-scan.mjs` without installing `typescript@5`, which fails closed (exit 1) on every TypeScript consumer.

### H3. Shared baseline ships 1,726 allowlist entries for a different project's tree [verified]
`.guardrails/silent-success-allowlist.json` (12,093 lines): entries reference `internal/` (1,456), `tests/` (225), `go/` (40), `cmd/` (5) paths that do not exist in this repo — a consuming project's allowlist committed into the upstream baseline every consumer inherits. Inert for other projects (coverage keys on exact file match) but it bloats every install, models the wrong workflow (project data belongs in the project's `.guardrails/` overlay), and desensitizes reviewers to allowlist diffs. Same finding as 2026-09-09 ("rad-gateway/gamerepo01 allowlists contaminated the shared baseline"), still present at scale.

### H4. `guardrails-scan.mjs` Rust `#[cfg(test)]` blanking breaks on the single-line module form [verified]
`scripts/guardrails-scan.mjs:152-174` (`blankTestModulesRust`): when `#[cfg(test)] mod tests {` shares one line, the opening brace is never counted (depth starts at 0 on the *next* line), the block exits after the first brace-balanced line, and the remaining test lines are scanned as production. Verified: `#[cfg(test)] mod tests {` + a `let password = "…"` two lines later → `[critical] PREVENT-003 … exit 1`; the multiline form is correctly clean. A gate meant to *stop* firing on test code fires on it, in the most idiomatic Rust test layout after the multiline one.

### H5. Pytest test files escape the file-size gate two ways [verified]
`scripts/regression_check.py:85-93`: `SOURCE_DIRS` has no `tests`/`test` entry, so in any project with a standard `src/`+`tests/` layout the test tree is never sized (verified: 550-line `tests/test_big.py`, `--staged --pre-commit` clean). And `regression_sizes.py:44-49` classifies tests via `rel_path.endswith((..., "test_*.py", ...))` — a literal glob inside `endswith` never matches, so a pytest file in a scanned directory is judged against SRC_HARD 500, not TEST_HARD 600 (verified: `src/test_helper.py` at 550 lines → ERROR "limit 500"). `TEST_HARD` is effectively dead configuration.

### H6. `spec_traceability.py` can never pass for Python code [verified]
`scripts/spec_traceability.py:9`: the marker regex is `//\s*spec:\s*…` — only `//`-style comments. `.py` is in `SCAN_EXTS`, but `# spec: <id>` never matches, so a Python consumer's blocking mode fails at 0% coverage no matter how the code is annotated. The generated advice (`findings_to_spec.py:142`) tells implementers to "mark the enforcing source with `// spec: <id>`" — a comment syntax Python doesn't have.

### H7. `deploy.sh` PyPI publish double-uploads and aborts after a successful publish [code-read]
`scripts/deploy.sh:304`: `python3 -m twine upload dist/* 2>/dev/null || python3 -m build && python3 -m twine upload dist/*`. Shell precedence makes this `(A || B) && C`: when the first upload *succeeds*, the final `&&` leg runs the same upload again; twine rejects the duplicate and `set -e` aborts the pipeline with a failure *after the immutable publish already happened* — the exact state the stage ordering exists to prevent. The first leg's `2>/dev/null` also hides the real error the retry logic claims to preserve, and `twine upload dist/*` re-uploads every artifact in `dist/`, including previously published ones.

### H8. `log_failure.py` writes project bugs into the upstream baseline by default [code-read]
`scripts/log_failure.py:44`: `DEFAULT_REGISTRY = DEVGATE_ROOT/.guardrails/failure-registry.jsonl` — inside the submodule. A consumer running the documented command appends *their* bug to the *shared* registry, which is precisely how the current baseline came to hold 12+ entries referencing other repos' files (`go/internal/engine/game.go`, `.github/workflows/ci.yml` of a game project, …) that now emit permanent stale-path warnings for every consumer (verified: `failure_registry_check.py` prints 12 "path not found" warnings on a clean checkout). The overlay contract exists (project `.guardrails/failure-registry.jsonl`) but the writing tool defaults to the wrong side of it.

## MEDIUM

### M1. `extracted-rules.json` — an entire ruleset nothing enforces [verified]
`.guardrails/prevention-rules/extracted-rules.json` (10 rules: PREVENT-GIT-001…006, PREVENT-SYS-001, PREVENT-SEC-001/002, PREVENT-SCOPE-001) is referenced only in the README tree listing. No script loads it (`rg extracted-rules scripts/ tests/` → only `gate_overlay.py`'s generic dir walk, which reads only `pattern-rules.json` and `semantic-rules.json`). These are also agent-*behavior* rules (no force-push, no rm -rf) that file scanning cannot enforce — they belong in the skill templates, which already cover them.

### M2. `silent-success-scan.sh` ignores the overlay contract it lives under [code-read]
The scan reads rules and allowlist only from `devgate_root/.guardrails/…` (`silent-success-scan.sh:36-37, 50-58`): no project-overlay merge (unlike every other gate via `gate_overlay.py`), and no `.guardrailsignore` support (unlike `guardrails-scan.mjs` and `game_regression.py`). A consumer cannot configure the gate without editing the submodule — the pattern the overlay contract exists to kill. Same for `schema-health-check.mjs`, whose only configuration path is "edit this file" inside the submodule — directly contradicting AGENTS.md's "Don't modify DevGate scripts".

### M3. `silent-success-rules.json` ships two families enabled, contradicting its documented contract [verified]
`silent-success-scan.sh:20-21` and the drift-scan header promise "EVERY family ships enabled:false, so a fresh DevGate install is GREEN". The data ships `go_return_nil_after_ignored_error` and `python_pass_todo_body` with `enabled:true`. A fresh consumer whose code matches either family fails the gate out of the box, against the documented opt-in.

### M4. `guardrails-compliance.yml` forbidden-file check treats globs as regex [code-read]
`FORBIDDEN_PATTERNS` (".env", "*.pem", "*.key", …) are passed to `grep -E`: `.env` matches any-char+"env" (`environment.yml`, `src/env.js`, and even `.env.example` — which the workflow's own message tells people to use), and `*.pem` degenerates to matching "pem" anywhere. A blocking gate with systematic false positives. Same file: the AI-attribution check splits commit bodies with `tr '---COMMIT_SEP---' '\n'` — `tr` maps *characters*, shredding every commit body at each `C,O,M,I,T,-,_…` letter, so the keyword scan runs on fragments (both false positives and false negatives).

### M5. Deploy gate stage 3 is documented as a gate but runs as a warning [code-read]
`deploy.sh:138` runs `schema-health-check.mjs … || echo WARN` — a schema failure (missing columns, FK violations) never blocks a database-backed deploy, while `schema-health-check.mjs:184-187` says "Deploy blocked" and `docs/RELEASE_GATE.md`'s stage table lists it as a gate. `npm run lint`/`cargo clippy` are likewise demoted to warnings in a pipeline named "full gate".

### M6. Artifact-verify passes vacuously on an empty contract [code-read]
`deploy.sh:262-276`: if the contract file exists but `must_contain` is absent/empty, the `while read` loop iterates zero times, `MISSING=0`, and "artifact verify OK" prints — the headline stage of the release pipeline green-lights a pack it asserted nothing about. Absent file → documented skip is fine; present-but-empty file → silent vacuous pass.

### M7. Version/changelog drift: v1.1.0 and v1.2.0 shipped with no CHANGELOG entries; VERSION file stuck at 1.0.0 [verified]
`git tag` shows v1.0.0, v1.1.0, v1.2.0; `VERSION` at HEAD reads `1.0.0`; `CHANGELOG.md` documents only `[1.0.0]`. Consumers pinning the submodule get a version file that disagrees with the tags, and there is no recorded delta for the last two releases.

### M8. Game-framework specs bundled in the language-agnostic framework, with no requirement IDs and referencing gates that don't exist [verified]
`openspec/specs/{game-regression,game-type-phase-matrix,per-screen-tracking}/spec.md` are Sword-of-Hope game-framework documents ("Keystone spec — drives all other devgate-game-framework gates" — no such gates exist here). They carry no `<!-- id: … -->` requirement IDs, so `spec_traceability.py` reports `0/0 requirements covered` — the traceability story the repo advertises doesn't cover its own shipped specs. `scripts/game-framework-README.md` is a leftover of the same merge (tells readers to `git submodule add … devgate-game-framework.git`).

### M9. Repo has no CI of its own [verified]
`.github/` contains only `FUNDING.yml`. Nothing runs the gates or the test suite on pull requests to the framework itself — PR #2 (v1.0.0) merged with zero checks — for a product whose entire premise is "gates must actually catch the failure class". Every consumer template in this repo enforces more than the repo enforces on itself.

### M10. `AGENTS.md` instructs consumers to violate the overlay contract [verified]
`AGENTS.md` "Adding Custom Rules" says to add rules to `.devgate/.guardrails/prevention-rules/pattern-rules.json` and its database section says to edit `scripts/schema-health-check.mjs` — while the README's overlay contract says projects must *never* edit the submodule and must use the project-root `.guardrails/` overlay, and AGENTS.md itself elsewhere says "Don't modify DevGate scripts". Rule counts are also stale (AGENTS.md/README say 29 pattern rules; the file ships 32).

### M11. `semantic-scan.mjs` walk has no symlink/realpath or unreadable-dir handling; `silent-success-scan.sh` reads every file as text [code-read]
Minor robustness: `semantic-scan.mjs`/`guardrails-scan.mjs` `walk()` throws on unreadable directories (the EACCES crash vector in C2); `silent-success-scan.sh`'s `rglob('*')` reads binaries as text over the whole tree with no size guard.

## LOW / COSMETIC

- **L1.** `guardrails-scan.mjs` `isCommentLine()` has a dead branch (lines 187-197 compute `beforeComment` and do nothing) and the "test-scope inversion" block (lines 230-235) is a no-op — the narrowing it describes never happens, so a production line containing the substring `test`/`latest` still gets suppressed by a test-flavored `forbidden_context`.
- **L2.** `guardrails-scan.mjs` COMMITTED-ENV flags `.envrc` (direnv config, routinely committed) as critical because it only checks `startsWith(".env")` minus three suffixes.
- **L3.** DevGate's own tree is not warning-clean: `PREVENT-024` fires on `tests/test_regression_check.py:45` on every self-scan.
- **L4.** `file-size-check.yml` uses `-ge` (500 lines exactly = violation) while `regression_check.py` uses `>` — a one-line disagreement between two gates with the same name; its SETUP header also references `scripts/check_file_sizes.sh`, which does not exist.
- **L5.** `secret-validation.yml`'s `.env` finder exempts only `.example`/`.template`, while `guardrails-scan.mjs` also exempts `.sample` and any `*template*` — the two .env gates disagree; `.env.sample` fails one and passes the other.
- **L6.** `.gitignore` ignores `Cargo.lock` — right for libraries, wrong default for the Rust *binary* projects this framework mostly serves; and it carries an agent-behavior rule (`PREVENT-DIST-001` no-.tgz) a gitignore cannot enforce.
- **L7.** `run-tests.mjs` creates a per-file `mkdtempSync` isolation dir it never uses (env never references it) — dead scaffolding, cleaned up but never load-bearing.
- **L8.** `failure_registry_check.py` accepts non-40-hex `fix_commit` values unvalidated ("unusual value — accept"), so the short SHAs `log_failure.py`'s own examples produce (`80b0c9b`) are never existence-checked.

## What is genuinely good

Overlay merge (`gate_overlay.py`) is implemented once and mirrored correctly on the JS side; the diff parser is hunk-accurate with real line numbers; registry regression patterns honor `file_glob`, `exclude_glob`, and `guardrails-allow`; invalid regexes warn instead of crashing gates; shallow-checkout diffs fail loud instead of passing vacuously (FAIL-3bc44d38 fix works); severity ladder is consistent across gates; `run-tests.mjs` flake adjudication correctly refuses to clear crash-before-tests files; 44/44 tests pass and `tests/test_guardrails_scan.mjs` locks the hardest scanner semantics with fixture projects.

## Not verified in this audit

- `smoke-gate.yml` end-to-end (needs a consuming app).
- Self-hosted runner quadlet on a live host (template review only).
- The `typescript@5` AST path of `semantic-scan.mjs` against a real React/TS codebase (SEMANTIC-001 false-positive rate).
